== Abstract

This document specifies the ANCHOR file format, an S-expression syntax for
encoding project recalibration and realignment directives within the
Hyperpolymath DEED/K9 ecosystem. ANCHOR files are ephemeral intervention
documents dropped into repositories when a project or AI agent has drifted
from its intended path. They provide authoritative, time-limited instructions
for scope correction, direction changes, and alignment verification.

ANCHOR shares its lexical layer with DEED but is _not_ a DEED: DEED files are
immutable epistemic records, while ANCHOR files are ephemeral, dated
interventions that reference a DEED chora as their target.

== Status of This Memo

This document specifies an experimental protocol for the Hyperpolymath estate.
It is a DRAFT (v1.0.0) and is not yet ratified. Discussion and suggestions for
improvement are requested.

The normative grammar for this specification is `anchor.abnf` (v1.0.0 DRAFT).

== Introduction

=== Purpose

The ANCHOR format addresses the need for authoritative, time-limited
intervention when:

* *Scope Drift* — a project or AI agent has expanded beyond its intended scope
* *Direction Change* — a strategic pivot requires explicit realignment
* *Stock-Taking* — a periodic review and verification of alignment is due
* *Emergency Halt* — a critical issue requires an immediate stop
* *Course Correction* — an explicit override of accumulated context is required

In the estate's type-theoretic framing, a DEED is a *projection* of a repo's
actual state; the *fiber* over that declaration is everything the projection
lost. ANCHOR is the _is/ought join_ — the point where projection and fiber are
forced back together, issuing directives to close the gap.

=== Design Goals

Authoritative:: Carries superintendent-level authority for realignment.
Temporal:: Every ANCHOR is dated and time-limited, with explicit `:issued` and
  `:expires` fields.
Explicit:: Instructions are unambiguous and machine-readable.
Traceable:: Authority chain, purpose, and verification criteria are recorded.
Data, not code:: Despite S-expression syntax, ANCHOR files are parsed, never
  evaluated.

=== Relationship to Other Specifications

[cols="1,3", options="header"]
|===
| Specification | Relationship

| *DEED* (`*_chora.deed`)
| ANCHOR targets a specific repo chora via `:target-chora <uuid5>`. The chora
  provides the declared state (the "ought"); ANCHOR addresses drift from it
  (the "is"). ANCHOR NEVER modifies DEED files.

| *K9 Coordination* (`coordination.k9`)
| ANCHOR directives MAY instruct agents to update `coordination.k9` (e.g., add
  invariants, revise protected paths). ANCHOR itself is not a K9 section.

| *Estate chora* (`estate_chora.deed`)
| ANCHOR does not reference the estate chora directly; it targets a specific
  repo.
|===

The A2ML format family (`ANCHOR.a2ml`, `ANCHOR.scm` as a Scheme module) is
*superseded* by this specification.

== Terminology

=== Key Words

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174).

=== Definitions

ANCHOR File:: A file with the `.anchor` extension containing a single
  `(anchor …)` form in the syntax specified by this document. Typically named
  `ANCHOR.anchor` or `ANCHOR-<purpose>-<date>.anchor`.
Superintendent:: The authority responsible for project direction. MAY be
  human, corporate, or algorithmic. Has power to issue ANCHOR directives.
Intervention:: An authoritative action to correct project trajectory, encoded
  as an ANCHOR file.
Realignment:: The process of bringing project state into conformance with
  ANCHOR directives.
Target chora:: The DEED chora (identified by UUID5) that this ANCHOR
  addresses.

== File Structure

=== Overview

An ANCHOR file consists of:

. *Header* — one or more SPDX comment lines.
. *Anchor form* — a single top-level `(anchor …)` S-expression containing
  required fields and clauses.

The entire input MUST be consumed by a conforming parser (`anchor-file` in the
ABNF).

=== Header (SPDX Lines)

ANCHOR files MUST begin with at least one SPDX line. Each SPDX line uses the
double-semicolon comment prefix:

[source,scheme]
----
;; SPDX-FileCopyrightText: © 2026 Jonathan D.A. Jewell
;; SPDX-License-Identifier: MPL-2.0
----

Grammar reference: `header = 1*spdx-line`.

=== The `anchor` Form

The body of an ANCHOR file is a single S-expression whose head is the symbol
`anchor`:

[source,scheme]
----
(anchor
  :schema-version "1.0.0"
  :target-chora #u5"casket-ssg/v1.0.0"
  :issued "2026-04-09"
  :expires "2026-05-09"

  (authority    …)
  (purpose      …)
  (directives   …)
  (verification …))
----

An `anchor-form` MUST contain *exactly one* of each of the following:

* `:schema-version` field
* `:target-chora` field
* `(authority …)` clause
* `(purpose …)` clause
* `(directives …)` clause
* `(verification …)` clause

It MUST also contain `:issued` and `:expires` fields (see <<required-fields>>).
It MAY contain a `:supersedes` field and a `(target-review …)` clause.

=== Lexical Layer

The lexical layer — comments, whitespace, strings, symbols, keywords,
integers, booleans, UUID5 literals, dates, and lists — is imported from DEED
(`deed.abnf`) and reproduced in `anchor.abnf` for self-containment. Key
primitives:

[cols="1,2,2", options="header"]
|===
| Token | Form | Example

| keyword | `:` + symbol             | `:priority`
| symbol  | ALPHA followed by ALPHA/DIGIT/punctuation | `scope-arrest`
| string  | double-quoted UTF-8      | `"Halt scope expansion"`
| integer | optional `-` + digits    | `42`, `-1`
| boolean | `#t` or `#f`             | `#t`
| uuid5   | `#u5` + string           | `#u5"casket-ssg/v1.0.0"`
| date    | `YYYY-MM-DD`             | `"2026-04-09"`
| comment | `;` to end of line       | `; note`
|===

[[required-fields]]
== Required Top-Level Fields

=== `:schema-version`

REQUIRED. A string identifying the ANCHOR schema version this file conforms
to.

[source,scheme]
----
:schema-version "1.0.0"
----

=== `:target-chora`

REQUIRED. A UUID5 literal identifying the DEED chora that this ANCHOR targets.

[source,scheme]
----
:target-chora #u5"casket-ssg/v1.0.0"
----

Implementations SHOULD verify that this UUID matches the repository's DEED
chora before processing directives.

=== `:issued`

REQUIRED. The date on which this ANCHOR was created.

[source,scheme]
----
:issued "2026-04-09"
----

=== `:expires`

REQUIRED. The date on which this ANCHOR ceases to be mandatory and becomes
advisory only.

[source,scheme]
----
:expires "2026-05-09"
----

=== `:supersedes` (Optional)

OPTIONAL. A UUID5 literal identifying a prior ANCHOR that this one replaces.

[source,scheme]
----
:supersedes #u5"anchor/2026-03-01"
----

If present, implementations SHOULD verify that the referenced anchor has been
archived.

== Core Clauses

=== Authority (`authority`)

==== Purpose

Establishes who issued this ANCHOR and their authorisation.

==== Structure

[source,scheme]
----
(authority
  :superintendent "Jonathan D.A. Jewell"
  :role           "Project Owner"
  :contact        "jonathan@example.com"      ; optional
  :level          full                        ; optional
  :scope          "all repo files")           ; optional
----

Required fields: `:superintendent`, `:role`. +
Optional fields: `:contact`, `:level`, `:scope`.

==== Authority Levels (`:level`)

`full`:: MAY modify any target file or project direction.
`scoped`:: MAY only modify areas specified by `:scope`.
`advisory`:: Recommendations only; not mandatory.

=== Purpose (`purpose`)

==== Purpose

Explains why this intervention is needed.

==== Structure

[source,scheme]
----
(purpose
  :type            scope-arrest
  :summary         "Halt scope expansion and stabilize architecture"
  :symptoms        ("Feature creep in last 3 sprints"
                    "Test coverage declining")
  :desired-outcome ("Return to core value proposition"
                    "Stabilize before new features"))
----

Required fields: `:type`, `:summary`. +
Optional fields: `:symptoms` (string-list), `:desired-outcome` (string-list).

==== Purpose Types (`:type`)

`scope-arrest`:: Stop scope expansion.
`direction-change`:: Strategic pivot.
`stock-taking`:: Periodic alignment review.
`emergency-halt`:: Critical issue requires immediate stop.
`course-correction`:: Minor trajectory adjustment.

=== Directives (`directives`)

==== Purpose

Specific, prioritised instructions for what MUST happen.

==== Structure

[source,scheme]
----
(directives
  (directive
    :action      "halt-new-features"
    :priority    critical
    :phase       immediate
    :description "No new feature work until backlog cleared"
    :deadline    "2026-04-16")
  (directive
    :action      "review-architecture"
    :priority    high
    :phase       this-week
    :description "Review and update architecture decisions"))
----

A `(directives …)` clause MUST contain one or more `(directive …)` entries.
Each `directive-entry`:

* REQUIRED: `:action` (string), `:priority` (symbol).
* OPTIONAL: `:description` (string), `:deadline` (date), `:phase` (symbol).

==== Directive Priorities (`:priority`)

`critical`:: MUST be done immediately; blocks all other work.
`high`:: SHOULD be done within deadline.
`medium`:: Important but not blocking.
`normal`:: Standard priority.
`low`:: When time permits.

==== Directive Phases (`:phase`)

* `immediate`
* `this-week`
* `this-month`
* `ongoing`

Agents MUST execute directives in priority order (`critical` → `high` →
`medium` → `normal` → `low`), with `:phase` used for scheduling within a
priority band.

=== Target Review (`target-review`)

==== Purpose

Specifies which artefacts in the target chora need review and what to check.
OPTIONAL clause.

==== Structure

[source,scheme]
----
(target-review
  (review :target coordination-k9
          :required #t
          :focus    ("invariants" "protected-paths"))
  (review :target repo-chora
          :required #f))
----

A `(target-review …)` clause contains one or more `(review …)` entries. Each
`review-entry`:

* REQUIRED: `:target` (symbol identifying the artefact), `:required` (boolean).
* OPTIONAL: `:focus` (string-list of areas to examine).

[NOTE]
====
ANCHOR directives MAY instruct agents to _update_ `coordination.k9`, but
ANCHOR itself NEVER modifies DEED files.
====

=== Verification (`verification`)

==== Purpose

Defines the criteria and method by which realignment success is to be
confirmed.

==== Structure

[source,scheme]
----
(verification
  (criterion :name    scope-contained
             :measure "No new features in backlog")
  (criterion :name    state-accurate
             :measure "coordination.k9 matches reality")
  :method   "checklist"
  :reviewer "superintendent"
  :deadline "2026-04-16")
----

A `(verification …)` clause MUST contain one or more `(criterion …)` entries,
followed by optional trailing fields.

Each `criterion-entry`:

* REQUIRED: `:name` (symbol), `:measure` (string).

Optional trailing fields on the `verification` clause:

* `:method` (string) — how verification is performed.
* `:reviewer` (string) — who performs verification.
* `:deadline` (date) — by when.

== Execution Protocol

=== ANCHOR Discovery

Agents SHOULD check for `*.anchor` files:

* At session start.
* When directed to the repository root or `.machine_readable/`.
* After receiving `anchor` or `realign` commands.

=== ANCHOR Processing

When an ANCHOR file is found, an agent MUST:

. Parse and validate the file against `anchor.abnf`.
. Verify `:target-chora` matches the repository's DEED chora.
. Check `:expires` — if expired, treat directives as advisory only
  (see <<expiration>>).
. Check `:supersedes` — if set, verify the referenced anchor is archived.
. Acknowledge the `(purpose …)` to the user.
. Execute `(directives …)` in priority order.
. Perform `(target-review …)` as specified.
. Report status against each `(verification …)` criterion.

=== Supersession

A new ANCHOR file supersedes:

* Any prior ANCHOR referenced through the `:supersedes` chain.
* Accumulated context that conflicts with its directives.
* Cached assumptions about project state.

Only one ACTIVE ANCHOR SHOULD exist in a repository at any time. Superseded
ANCHORs SHOULD be archived, not deleted, to preserve the audit trail.

[[expiration]]
=== Expiration

Expired ANCHORs (where the current date is past `:expires`) SHOULD be treated
as advisory only. Agents SHOULD NOT execute directives from expired ANCHORs
without explicit user approval.

== File Naming

* `ANCHOR.anchor` — the currently active anchor (only one at a time).
* `ANCHOR-<purpose>-<YYYY-MM-DD>.anchor` — dated anchor, typically for
  archives.

Examples:

* `ANCHOR.anchor`
* `ANCHOR-scope-arrest-2026-04-09.anchor`
* `ANCHOR-direction-change-2025-12-15.anchor`

ANCHOR files SHOULD live in the repository root or in `.machine_readable/`.

== Security Considerations

=== Authority Verification

Implementations SHOULD verify the `:superintendent` field in `(authority …)`
against a list of known project owners for the target chora.

=== Expiration

ANCHOR files MUST have `:expires` dates. Expired ANCHORs are advisory only;
implementations SHOULD prompt for explicit user approval before executing
expired directives.

=== Audit Trail

All ANCHOR processing (discovery, parsing, directive execution, verification
results) MUST be logged for later review.

=== No Self-Execution

ANCHOR files are *data*, not code. Despite their S-expression syntax, they
MUST NOT be evaluated as Scheme (or any other language). Conforming parsers
construct an abstract syntax tree and do not `eval` any portion of it.

=== Encoding

ANCHOR files MUST be UTF-8 encoded without a BOM. Parsers MUST reject files
containing NUL bytes or invalid UTF-8 sequences.

== IANA Considerations

=== Media Type Registration

Type name:: `application`
Subtype name:: `anchor+sexp`
Required parameters:: None
Optional parameters:: `charset` (default `UTF-8`), `version`
Encoding considerations:: UTF-8 text
Security considerations:: See <<_security_considerations>>.
Published specification:: This document
File extension:: `.anchor`
Magic:: None (identified by extension and by the `(anchor …)` head form)

== Conformance

An implementation is *ANCHOR-conformant* if:

. ANCHOR files are discovered at appropriate times.
. Files are parsed and validated against `anchor.abnf`, with the entire input
  consumed.
. `:schema-version`, `:target-chora`, `:issued`, and `:expires` are present
  and well-formed.
. Exactly one of each required clause (`authority`, `purpose`, `directives`,
  `verification`) is present.
. Authority and target-chora are validated before executing directives.
. Directives are executed in priority order.
. Optional `target-review` is performed when present.
. Each verification criterion is checked and reported.
. Expired ANCHORs are treated as advisory only.
. All processing is logged.
. ANCHOR content is treated as data — never evaluated as code.
