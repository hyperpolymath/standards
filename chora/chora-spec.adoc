== What Is a Chora?

A *chora* (from Plato's *Timaeus*: the receptacle that receives and
gives shape to forms) is a DEED file that declares identity, vocabulary,
and provenance for a scope of the estate.

There are two kinds:

* *Estate chora* (`estate_chora.deed`) — the single estate-wide
  vocabulary declaration site. One per estate.
* *Repo chora* (`*_chora.deed`) — a per-repository identity record
  that beholds the estate chora. One per repository.

== Grammar

Choras are DEED files. They parse under `deed.abnf` with the following
dispatch rules:

[cols="1,1,1"]
|===
| Filename | Doc Head | DEED Spec Reference

| `estate_chora.deed`
| `estate-deed`
| §5 (exact match, tested first)

| `<stem>_chora.deed` (stem ≠ `estate`)
| `repo-deed`
| §5 (glob match, after exact)
|===

== Estate Chora

=== Purpose

The estate chora is the *one declaration site* for all shared vocabulary:
types, tropes, lattices, and universal invariants. No other file in the
estate may declare vocabulary; all other deeds reference it.

=== Required Fields

[cols="1,1,2"]
|===
| Field | Type | Purpose

| `:schema-version`
| STRING
| Format version (structurally first)

| `:canonical-name`
| STRING
| Estate identifier

| `:estate-uuid`
| UUID5
| Deterministic estate identity
|===

== Repo Chora

=== Purpose

A repo chora records what a repository *is*: its identity, provenance,
and relationship to the estate vocabulary. It is an epistemic record,
not an operational one (operational rules belong in `coordination.k9`).

=== Required Fields

[cols="1,1,2"]
|===
| Field | Type | Purpose

| `:schema-version`
| STRING
| Format version (structurally first)

| `:canonical-name`
| STRING
| Repository identifier

| `:repo-uuid`
| UUID5
| Deterministic repo identity

| `:beholding-chora`
| UUID5
| Reference to the estate chora
|===

=== Recommended Clauses

* `(provenance ...)` — author, creation date, warrant
* `(project ...)` — description, languages, license

== The One Declaration Site Rule

Vocabulary is declared in `estate_chora.deed` and *nowhere else*.

* Repo choras *reference* the estate chora via `:beholding-chora`.
* Praxis deeds *reference* the estate chora via `:beholding-chora`.
* No deed may re-declare types, tropes, or lattice elements that
  belong to the estate vocabulary.

*Rationale:* Two declaration sites with no precedence between them
is not a layering problem — it is an ambiguity.

== The "Not a Layer" Topology

The chora is not a layer in a stack. It is a *hub*:

----
        estate_chora.deed
                 |
   +-------------+-------------+
   |                           |
   v                           v
 REPO CHORAS            PRAXIS DEEDS
 (identity)             (rules)
   |                           |
   v                           v
 K9 COORDINATION         EMISSIONS
 (operations)           (derived state)
----

== Relationship to K9 Coordination

[cols="1,2"]
|===
| Concern | Rule

| Identity
| K9 `project.deed_ref` points to the repo chora. The chora is
  authoritative for identity; K9 is authoritative for operations.

| Invariants
| K9 invariants are operational (what agents must not do). Estate
  chora invariants are universal (what is structurally true). K9
  invariants SHOULD NOT duplicate estate invariants.

| Terminology
| K9 terminology is project-local. Estate chora terminology is
  estate-wide. K9 terminology SHOULD NOT contradict estate terminology.

| Mutability
| Repo choras are immutable (versioned records). K9 `coordination:`
  is mutable. All other K9 sections are stable.
|===

== Validation Rules

1. `estate_chora.deed` MUST parse as `estate-deed`.
2. `*_chora.deed` (stem ≠ `estate`) MUST parse as `repo-deed`.
3. Every non-estate deed MUST have a `:beholding-chora` UUID5.
4. The `:beholding-chora` UUID MUST resolve to an existing
   `estate_chora.deed` whose `:estate-uuid` matches.
5. No deed other than `estate_chora.deed` MAY declare estate
   vocabulary (types, tropes, lattice).
