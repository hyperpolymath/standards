IANA Media Type Registration: application/vnd.k9.coordination
=========================================================
SPDX-License-Identifier: CC-BY-SA-4.0

This file is the canonical registration document for
application/vnd.k9.coordination.  It lives beside the specification it
registers; there is no second copy.

NOTE: The k9-coordination dialect shares the "K9!" magic with
application/vnd.k9 but is a different format, so it is registered as its
own subtype rather than as a parameter of vnd.k9 (owner ruling,
2026-10-13).  Parameters are routinely dropped by file-type detectors,
which would label coordination files as Nickel components; a subtype
survives that, and lets each type state its own encoding and security
considerations.

STATUS: NOT FILED; file together with application/vnd.k9.

Prepared: 2026-10-13 (Revision 1)
Prepared By: Jonathan D.A. Jewell <j.d.a.jewell@open.ac.uk>

Type name:
  application

Subtype name:
  vnd.k9.coordination

Required parameters:
  None

Optional parameters:
  None

Encoding considerations:
  8bit

  UTF-8 text with no NUL octet.  Line 1 is exactly the three octets
  "K9!" (0x4B 0x39 0x21), then one or more "# SPDX-" comment lines,
  then the body.  The body is a line-oriented, YAML-like language with
  its own ABNF grammar; it is NOT YAML and MUST NOT be handed to a
  general YAML parser.  Indentation is exactly two spaces per level;
  tabs are invalid.  Line endings are LF or CR+LF.

Security considerations:
  A coordination file is pure data.  The grammar admits no executable
  content, no include or import directive, no evaluation form and no
  opaque payload.  Processors MUST NOT execute anything found in it.

  Coordination files are read by automated agents (AI coding assistants)
  to decide what they may and may not change in a repository, so:

  (a) Processors MUST treat a coordination file as untrusted input.  Its
      invariants, protected paths and "do not create" rules are claims
      by whoever last edited the file, not grants of authority; an agent
      MUST NOT infer any privilege from them.

  (b) A coordination file can steer an agent away from a change, so a
      tampered file can be used to suppress a legitimate fix.  Consumers
      that act on it SHOULD read it from the reviewed default branch,
      not from an unreviewed change.

  (c) Generators that turn a coordination file into tool-specific
      instruction files SHOULD escape or quote its strings for the target
      format, so that text in the file cannot become instructions the
      file's author did not write.

  Privacy: coordination files name agents, work areas and dates, and
  usually live in public repositories.  They SHOULD NOT carry secrets,
  credentials or personal data.

Interoperability considerations:
  Companion type: application/vnd.k9.  Both types begin with the "K9!"
  magic.  A reader MUST classify a magic-bearing file by its first
  significant line before validating it (K9 Component Contract
  Specification, "K9-E005 - the discriminator"): a bare "key:" line is
  this type; a Nickel term is application/vnd.k9.  A "---" line is
  routed to this type and then rejected by its grammar.

  The conventional filename is "coordination.k9" at the repository
  root, which file-type detectors can match literally.

Published specification:
  K9 Coordination File Specification v1.2.0:
  https://github.com/hyperpolymath/standards/blob/main/2-protocols/k9-coordination/spec/COORDINATION-K9-SPEC.adoc

  Formal grammar (ABNF, normative for parsing):
  https://github.com/hyperpolymath/standards/blob/main/2-protocols/k9-coordination/spec/abnf/coordination-k9-grammar_v1.2.abnf

Applications which use this media type:
  - The k9-coordination generator, which emits per-tool AI-agent
    instruction files from a coordination.k9
  - k9-init, which scaffolds coordination.k9 files
  - The K9 reference validator, k9-validate.sh, which routes these files
    to the coordination grammar

  Reference implementation:
  https://github.com/hyperpolymath/standards/tree/main/2-protocols/k9-coordination

Fragment identifier considerations:
  None defined.  Processors encountering a fragment SHOULD treat it as
  unresolvable rather than raise an error.

Restrictions on usage:
  None.
