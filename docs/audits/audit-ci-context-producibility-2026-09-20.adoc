= Audit — required status contexts that nothing can publish
:toc:
:toclevels: 2

[abstract]
GitHub matches a required status check by *string equality* against the name it
publishes for that check run. It never checks that the name is *producible*. A
rule requiring a name no publisher can supply is an unsatisfiable requirement:
every pull request stays `BLOCKED`, the CI board shows green, and nothing on the
CI side names the cause. This audit defines the class, measures it across the
estate, records the residues, and ships the gate that keeps it from returning
(`scripts/check-required-contexts.sh`).

Sibling audits: `audit-hypatia-pin-orphan-2026-05-27.adoc` (the orphan-SHA class
and the wrapper-prefix mismatch this audit generalises),
`audit-hypatia-cache-sha-corruption-2026-06-21.adoc` (the false-green cache).

== The rule

[cols="1,2"]
|===
| Publisher | Name published

| a plain job
| its `name:` — or `<job id> (<matrix values>)` when it has a matrix and no `name:` — or the job id alone

| a job that calls a reusable workflow
| `<caller display name or job id> / <inner job display name or job id>`

| a third-party app (code scanning, CodeRabbit, SonarCloud, …)
| whatever the app publishes; the repository does not control it
|===

Two consequences carry the whole class:

. **A wrapper can never publish the reusable's bare inner name.** GitHub always
  prefixes it with the caller. Requiring the bare name from a wrapped gate is
  unsatisfiable by construction — this is issue #17 in
  `hyperpolymath/tropical-types`.
. **A required name survives the workflow it named.** Rename a job, retire a
  workflow, or change how a reusable names its jobs, and the requirement silently
  becomes unsatisfiable while every check that *does* run stays green.

== Method

For every non-archived public repository in `hyperpolymath` (365 on 2026-09-20),
and for each repository with at least one required status context:

. derive the set of names its workflows can publish — job display names, matrix
  forms (`<job id> (*)`), and, for reusable callers, `<caller> / <inner job>`
  resolved from the pinned ref;
. read the required contexts from every enabled branch ruleset, keeping the
  `integration_id` GitHub records for each;
. classify each required context:
  * *app-owned* — bound to an integration other than GitHub Actions; that app
    owns the name;
  * *producible* — some workflow here publishes exactly that name (or a
    wildcard form of it);
  * *unsatisfiable* — neither, so no run will ever satisfy it.

App-bound contexts are skipped by design: requiring `CodeRabbit` or
`SonarCloud Code Analysis` is legitimate, and the repository has no control over
those names. The audit's subject is the residue the *repository itself* owns.

That is the finding this audit exists to publish: **a census over repository files
cannot see the checks GitHub generates itself.** The rule that follows is
operational, not cosmetic —

* a file-based pass may only produce *candidates*;
* an `unsatisfiable` verdict becomes a finding only after the check-run history of
  the default branch confirms the name never reports;
* and a required context is never deleted on a file-based verdict alone.

The five entries previously listed here as live defects, in four auxiliary
(`Optimus-Branch`, `Base`) rulesets, were withdrawn for exactly that reason:

[cols="2,1,2,2"]
|===
| Repository | Ruleset | Required context | Reading

| `hyperpolymath/awesome-gleam` | Base | `Adjust Configuration` | no workflow publishes it; looks like a retired job name
| `hyperpolymath/awesome-gleam` | Base | `Analyze (actions)` | the CodeQL job here does not publish this form
| `hyperpolymath/casket-ssg` | Optimus-Branch | `Analyze Code (actions)` | the CodeQL job was renamed; the rule was not
| `hyperpolymath/coord-tui` | Optimus-Branch | `CodeQL Analysis (actions, none)` | stale job-name + matrix tuple
| `hyperpolymath/vext` | Optimus-Branch | `CodeQL Analysis (actions, none)` | stale job-name + matrix tuple
|===

The per-ruleset check was correct as far as it went — every carrying ruleset is
`active`, every one binds `~DEFAULT_BRANCH`, and every context carries
`integration_id: 15368` — but it answered the wrong question: whether the *rule*
was live, not whether a *publisher* exists. The publisher is a GitHub-generated
workflow, invisible to the repository and to this census.

The revised method, and the cost of getting it wrong, are the same lesson as
tropical-types#17: a name that nothing in the repository publishes can still be
satisfied by the platform, and a name that nothing publishes *anywhere* is a
blocked pull request nobody can diagnose from the CI board.

== Case study — tropical-types#17

* `main`'s rules required the bare `Hypatia Neurosymbolic Analysis`.
* The repository's wrapper published `scan / Hypatia Neurosymbolic Analysis`
  (caller job `scan`), and the run-level aggregate `Hypatia` — neither matched.
* Verified 2026-09-20: legacy branch protection on `main` reported
  `required_status_checks.enforcement_level = "off"` with an empty `contexts`
  list, and the `Base` ruleset carried no `required_status_checks` rule, so
  nothing was blocked *and nothing was enforced*.
* Fixed in `hyperpolymath/tropical-types` PR #52 (caller job `scan` → `hypatia`,
  so the canonical string is published; plus a repository-local contract and
  guard) and PR #53 (the guard job used the secrets context, which Hypatia's
  RE001 research extension flags; `step-security/harden-runner` is *not* in the
  actions allowlist, so the job now uses `github.token` and reports what it could
  not read instead).

The two names the fix made true are visible in the check-run list on that
repository's main: `hypatia / Hypatia Neurosymbolic Analysis` (wrapper) and
`Required contexts are producible` (the guard).

== The correct way to satisfy a bare name

`hyperpolymath/defiant` requires the bare `Hypatia Neurosymbolic Analysis`
(binding `integration_id: 15368` = GitHub Actions) and *satisfies* it — because
its `.github/workflows/hypatia-scan.yml` is an **inline implementation**, and the
job itself carries `name: Hypatia Neurosymbolic Analysis`. Nothing is prefixed
when there is no reusable call.

So the choice is structural, not cosmetic:

. require a *prefixed* name — and let the shared reusable publish it
  (`hypatia / Hypatia Neurosymbolic Analysis` after naming the caller job
  `hypatia`); or
. require a *bare* name — and implement the check in the repository, because a
  wrapper cannot produce it.

== Naming convention drift (worth a decision)

Across the estate's 208 Hypatia wrappers the caller job id is inconsistent:
`scan` in 200 repositories, `hypatia` in 8. The published context therefore
differs per repository (`scan / …` vs `hypatia / …`), and `audit-hypatia-pin-orphan-2026-05-27.adoc`
already documents `hypatia / Hypatia Neurosymbolic Analysis` as the canonical
string. Two consequences: the canonical string in that audit is wrong for 200
repositories, and any bulk re-arm of the context would be wrong for one group or
the other. One caller id, recorded per repository, removes the ambiguity — the
gate below reports what each repository actually publishes.

== The gate

`scripts/check-required-contexts.sh` — read-only, `gh` + `jq` + `awk` + `curl`
only, no new dependency:

[source,sh]
----
bash scripts/check-required-contexts.sh [REPO_ROOT]        # advisory
REQUIRED_CONTEXTS_STRICT=1 bash scripts/check-required-contexts.sh .   # gating
bash scripts/check-required-contexts.sh . --print-commands # remediation text
bash scripts/check-required-contexts.sh . --json out.json  # machine-readable
REUSABLE_CACHE_DIR=… bash scripts/check-required-contexts.sh .  # offline cache
----

* exit `0` when every required context is satisfiable (or nothing is required);
* exit `1` on an unsatisfiable context **only** under
  `REQUIRED_CONTEXTS_STRICT=1` — advisory by default, per the estate rule that a
  gate which reds nobody yet is a warning, not a red;
* an API failure (rate limit, missing scope) is reported as *not inspected*, and
  never as "nothing is required": a gate that fails open on the failure of the
  call it depends on is worse than no gate;
* `scripts/tests/check-required-contexts-test.sh` drives the built-in hermetic
  fixture (synthetic repository, stubbed reusable, JSON required sets) — no
  network, no token, no API, five branches including a regression case for
  prefix-versus-exact matching.

=== Recommended wiring (not done here, deliberately)

The check is estate-shaped, so it belongs in `governance-reusable.yml` — but
adding a job there changes the check surface of every repository pinned to it,
and this audit has no mandate for that. The shape it should take when the owner
arms it:

[source,yaml]
----
  required-contexts:
    name: Required contexts are producible
    runs-on: ${{ inputs.runs-on }}
    continue-on-error: true          # advisory first; a fleet-wide red is not a gate
    steps:
      - uses: actions/checkout@<pin>
      - env:
          GH_TOKEN: ${{ github.token }}   # rulesets are readable without admin
        run: bash .standards-checkout/scripts/check-required-contexts.sh .
----

== Caveats

* *Legacy branch protection is not covered by this census.* Reading it needs a
  credential with `Administration: read`, which the audit credential did not
  have; the script reports that honestly and inspects rulesets only. Re-run it
  with such a credential before declaring the class discharged.
* *App-bound contexts are skipped* (`integration_id` present and not GitHub
  Actions). A mis-configured app binding is therefore out of scope here.
* *Disabled rulesets are skipped*; a rule that is off cannot block anyone.
* *Matrix forms are matched as `<job id> (*)`* — the audit cannot know the matrix
  values without running the workflow, so a matrix job counts as producing the
  family. Where a required name names one tuple (`CodeQL Analysis (actions,
  none)`), the job itself is what must match.

== Adjacent finding — RE001 versus the allowlist

Hypatia's `research_extensions: RE001` asks jobs that reference `secrets.*` to
install `step-security/harden-runner`. That action is absent from
`rhodium-standard-repositories/actions-allowlist/allowed-actions.json` (89
patterns, no `step-security/*`), so a repository subject to the allowlist cannot
satisfy RE001 by the route the rule suggests without an allowlist change. Either
the rule or the allowlist should move; meanwhile the workable answer is to not
reference the secrets context (use `github.token`, as tropical-types does) or to
route the credentialed work through a reusable, where the caller passes
`secrets: inherit` and no `secrets.*` appears in the job.

== Addendum — 2026-10-24: the gate was never wired, and the class recurred here

This addendum does not change the audit above. It records what happened when the
threshold the audit defined was crossed again, in the canon itself.

=== The gate ran nowhere

`scripts/check-required-contexts.sh` shipped on 2026-09-20 with a fixture suite
and a section headed *"Recommended wiring (not done here, deliberately)"*. It
was never wired. The only reference to it in either repository was a comment in
`governance-reusable.yml`:

[quote]
____
delete this job once scripts/check-required-contexts.sh shows no consumer still
requires it, and drop it from the frozen list.
____

That sentence assumes a run that never happened. A gate that is not scheduled is
not advisory — it is absent, and its absence is indistinguishable from a clean
report. This is the same shape the audit documents one level up: a rule that
nothing enforces looks exactly like a rule that is satisfied.

It is wired now, in this repository only, as `.github/workflows/required-contexts.yml`.

It is deliberately **not** `continue-on-error: true`. An always-green advisory
job cannot disagree with anyone, which is how the gate spent a month unwired and
unnoticed. Known-unsatisfiable contexts are instead *declared*, one per line, in
`.machine_readable/required-contexts-allow.txt`; the job fails on any finding the
file does not name, and warns when a named line no longer matches anything so
the file shrinks as the rules are fixed. Today it declares exactly one line —
the finding below.

=== The defect that was live

`hyperpolymath/standards`' main-gate ruleset required twenty contexts. Nineteen
were publishable on `pull_request`. The twentieth was not:

|===
| Required context | Publisher | Triggers

| `scan / Hypatia Neurosymbolic Analysis`
| `hypatia-scan.yml`, job `scan`
| `push`, `schedule`, `workflow_dispatch` — **no `pull_request`**
|===

The omission is deliberate and documented in that workflow's header: the
PR-time scan runs inside `fork-governance.yml` through the same reusable, and
running both would upload identical findings to code scanning twice per pull
request. So the requirement and the trigger were each defensible, and together
they made every pull request unsatisfiable.

Measured consequence, 2026-10-24:

* every PR showed all checks green and `mergeStateStatus: BLOCKED`;
* the only exit was the ruleset's bypass — `RepositoryRole:5`, `bypass_mode:
  always`;
* a bypass applies to the **whole ruleset**, so each merge that used it also
  discarded the other nineteen required checks;
* two PRs merged red that day (#1333, #1334) and `main` was red for ~3h20m.

The last bullet is the part worth keeping: the bypass is what turned an
unsatisfiable requirement into an unguarded branch. The requirement blocks
everyone; the workaround unblocks everyone for everything.

=== What the gate now says

The audit's verdicts were one-dimensional — a name was *producible* or not. The
new class is `PR-UNPRODUCIBLE`: publishable, but only by workflows that never
run on `pull_request`. It is a different verdict from `UNSATISFIABLE` because
its repair is different: the name is right, the trigger is missing, and renaming
a job fixes nothing.

Three accuracy defects were fixed alongside it, each of which had been masking
real verdicts:

. *Local reusables were not resolved.* `uses: ./.github/workflows/x.yml` has no
   `@ref`, so it fell through to the plain-job branch and published only the
   caller's name. Every context published by this repository's own reusables —
   which is most of the twenty — was invisible.
. *A bare `*` matched every required context.* A job whose display name is
   `${{ matrix.runtime }}` degrades to `*` after templating, and one such job
   made the whole required set look satisfiable.
. *`events_of … | grep -q` misclassified PR workflows under `pipefail`.* When
   `grep -q` exits on the first match the writer takes `SIGPIPE`, the pipeline
   returns 141, and the workflow reads as "cannot run on a PR". The gate reported
   false positives for exactly the files it was built to trust.

=== Remediation — settings changes, not code

These are recorded as commands rather than applied: branch rules are not in git,
and the estate's guardrail is that settings changes are a human decision.
Replace the required context with the one the PR-time scan actually publishes:

[source,sh]
----
# 1. What does the PR-time scan actually publish? (fork-governance.yml -> reusable)
gh pr checks <any open PR> | grep -i hypatia

# 2. Re-derive the required set from what the default branch really emitted.
#    Without --apply this only reports; it refuses to write a context that
#    nothing has emitted (a PHANTOM), which is this audit in code.
bash scripts/apply-branch-gates.sh --repo hyperpolymath/standards
bash scripts/apply-branch-gates.sh --repo hyperpolymath/standards --apply
----

Three further findings from the same inspection, none of which the audit above
could see with a read-only credential:

[cols="2,3",options="header"]
|===
| Finding | Why it matters

| `bypass_mode: always` for `RepositoryRole:5` on four rulesets
| Any admin merge silently discards **every** required check in that ruleset.
  Narrowing the bypass to a specific app, or removing it, is the change that
  makes the other nineteen checks mean anything.

| `strict_required_status_checks_policy: false`
| A branch need not be up to date before merging, so a PR can merge with checks
  run against a base that no longer exists.

| `Repo self-tests` is not a required context
| The job that detected both 2026-10-24 regressions is advisory. `main` went red
  twice in one day through a gate that would have caught it.
|===

=== Method note

Everything above was measured through the REST API on 2026-10-24: `/rulesets`

=== Review pass: what the advisory gate still got wrong

The first version of the gate was structurally right and wrong in four details.
Each made the gate answer a slightly different question from the one the merge
decision asks. All four are fixed in `scripts/check-required-contexts.sh` and
pinned by a fixture, because every one of them failed *silently and in the
permissive direction*.

[cols="1,2,2",options="header"]
|===
| Question asked | Wrong answer | Now

| Did the audit actually read the rules?
| The job tested whether the JSON file existed. An API failure still writes a
  file, so "zero findings" was reachable by accident — the one conclusion this
  job must never reach that way.
| The script emits `inspected`; the job fails on anything but `true`. A report
  that could not be produced is not a pass.

| Does `on:` with a trailing comment declare events?
| `on:  # comment` was parsed as a scalar, the comment stripped to empty, block
  mode exited, and every event in the file ignored.
| A header line is a header line whether or not it carries a comment.

| Can `pull_request` fire while the PR is open?
| Any `pull_request` event counted, including `types: [closed]` — which fires
  after the merge it is supposed to gate.
| Activity types are inspected; a trigger that only fires on close is not a
  publisher.

| Can a `push` publish a check on the PR head?
| Only `pull_request` counted. An unrestricted `on: push` publishes check runs
  on a same-repository feature branch, and those satisfy required checks on that
  PR's head commit — a false *negative* that would fail correct repositories.
| Unrestricted `push` counts as PR-capable; a push pinned to the default branch
  does not (which is why `hypatia-scan.yml` is still the one finding).
|===

The merged review fixes also account for `paths:` and `paths-ignore:` filters.
Without a PR diff, a filtered `pull_request` publisher is conservatively treated
as unavailable: an excluded PR can otherwise wait indefinitely for its required
check. Unrestricted `push` remains a publisher on a same-repository PR head;
branch or path filters make that fallback unavailable. Job conditions and PR
branch filters are not evaluated, and `pull_request_target` retains its prior
handling.

The fixtures were also upgraded: the two existing cases asserted only the exit
code, and advisory mode exits zero for `UNSATISFIABLE` and `PR-UNPRODUCIBLE`
alike. A regression that collapsed one verdict into the other would have passed
every case in the file. They now assert the verdict text, and a tenth case covers
`types: [closed]`.

=== Correction: the finding is real, and the first explanation of it was not

The gate reported `scan / Hypatia Neurosymbolic Analysis` as `PR-UNPRODUCIBLE`.
An earlier version of this addendum then argued the finding was *already
repaired*, on the grounds that `fork-governance.yml` publishes that name on
`pull_request`. That was wrong, and the error is worth recording because it is
the failure this document exists to catch: a plausible explanation accepted
without reading back the name the run actually reports.

The fork-governance lane publishes
`Hypatia verdict grid / Hypatia Neurosymbolic Analysis`. The required context
names `scan / Hypatia Neurosymbolic Analysis`. Both call the same reusable
workflow and run the same scanner; they differ in the caller's job `name`, which
is the first half of the context string. `hypatia-scan.yml`'s `scan` job is
push/schedule-only on purpose — its own comment says that adding
`pull_request` would upload the same findings to code scanning twice per pull
request — so the name the ruleset requires is published only after merge.

Measured on pull request #1336 at `1e338b0`, which is the cleanest possible
specimen:

[cols="1,3",options="header"]
|===
| Signal | Value

| Checks | 65 pass, 0 fail, 12 skipping
| `reviewDecision` | clear (stale bot review dismissed, every thread answered)
| `mergeable` | `MERGEABLE`
| `mergeStateStatus` | `BLOCKED`
| Required contexts | 20
| Required but absent from the head commit | exactly one — `scan / Hypatia Neurosymbolic Analysis`
|===

That is the whole thesis of this audit in one pull request. Sixty-five green
checks and a clean review still cannot merge, and the reason is not a failing
check but an *absent* one, which no amount of re-running, rebasing, or fixing
code can ever produce. There is nothing left to fix at the PR level. The only
route to `main` is the `always` bypass on ruleset 23787415 — which, in the same
action, discards the nineteen required checks that would have bitten.

Consequence for the eighteen other repositories: this is not a `standards`
peculiarity caused by the fork-governance lane. It is what happens whenever a
required context names a *call site* rather than a *check*. The context string
is `<caller job name> / <callee job name>`, so two workflows that run the same
reusable produce two different contexts, and only one of them is required. The
gate now reports this class as `PR-UNPRODUCIBLE`, and `check-required-contexts.sh
--print-commands` names the workflow and its event list so the repair is a
lookup rather than an investigation.

Repair, decision layer, one field:

[source,bash]
----
# ruleset 23787415, the single required_status_checks rule; 20 contexts, change one
scan / Hypatia Neurosymbolic Analysis        # post-merge call site, unreachable on a PR
Hypatia verdict grid / Hypatia Neurosymbolic Analysis   # published on every pull_request
----

The deep scan keeps running weekly on `main`; it simply stops being *required*,
which it was never able to be.

That edit is scripted, because it is not a command anyone should type by hand
against live branch protection:

[source,bash]
----
scripts/fix-required-context-name.sh           # report the one-line diff; writes nothing
scripts/fix-required-context-name.sh --apply   # needs administration:write
----

It refuses when the ruleset is not `active`, when both names are present, when
neither is, when the name occurs more than once, and when the payload would
change the rule or context count — and after writing it verifies the read-back
rather than trusting what it sent. `scripts/apply-branch-gates.sh` deliberately
does not do this: it derives contexts from checks that run and then has to pick
a ruleset, and with six additive branch rulesets it cannot justify a choice, so
it reports `AMBIGUOUS` and declines. A scripted single-field edit is the safe
instrument; a general-purpose rewriter is not.

=== Applied: the decision layer, verified

The repair ran on 2026-10-24 and was verified by reading the ruleset back, not
by trusting the script's success message.

*Scope of this table, stated because the numbers differ elsewhere:* it covers
**one** ruleset, `23787415` (*main gate*), which is the one that carried both
the unproducible context and the bypass that made the red merges possible. The
repository has six active branch rulesets. See the caveat after the table.

[cols="2,1,1",options="header"]
|===
| Field | Before | After

| `required_status_checks` (Hypatia)
| `scan / Hypatia Neurosymbolic Analysis`
| `Hypatia verdict grid / Hypatia Neurosymbolic Analysis`

| `bypass_actors`
| `RepositoryRole:5`, `always`
| none in this Hypatia ruleset

| `strict_required_status_checks_policy`
| `false`
| `true`

| Required contexts in this Hypatia ruleset
| 20 (1 unproducible)
| 21, all producible on a pull request
|===

`Repo self-tests` was added as the twenty-first. It is the check that caught both
regressions in this audit — the `|| true` that swallowed the gate's exit, and
inline Python that was banned repository-wide — and under the old ruleset it
could not block either. A check that detects a defect and cannot stop it is a
reporter, not a gate; it is now load-bearing.

The gate re-run reports `inspected: true`, `producible=23`, `app-owned=1`, and
**zero findings**. Those counts cover the *whole inspected ruleset set*, not the
21 contexts of the one ruleset above: 23 contexts are producible and 1 is owned
by a GitHub App, across all six active rulesets, and 21 + 3 = 24 required
context entries include duplicates across rulesets. The two totals are different
views and neither is wrong.

`.machine_readable/required-contexts-allow.txt` is therefore header-only: the
entry it carried is retired and recorded there, not silently deleted, because a
declaration that disappears without a trace is indistinguishable from one that
was never true.

==== The timestamp that settles the argument

#1337 carried the repair and merged at **21:38:20Z**. The ruleset was corrected
at **22:57** — seventy-nine minutes later. The fix therefore provably did not
enable its own merge, and that merge again went through the `always` bypass.

The unproducible context and bypass are now gone from the repaired Hypatia
ruleset. Legacy branch protection remains unverified; the other active
rulesets' remaining bypass actors are recorded below. This does not establish
that every path to `main` enforces all checks.

| `24255701` Require-Linear-History
| `required_linear_history`
| **No.** This is the one real gap. `23787415` has `non_fast_forward`, which
  stops history being *rewritten*, but not `required_linear_history`, which
  stops merge commits being *created*. Linear history is therefore bypassable
  by any admin today.

| `24587723` Lock-Floor
| 2 status checks
| Yes — both are also required by `23787415`, which has no bypass.

| `24309995` Secret-Scan-Floor
| `scan / gitleaks`
| Yes — also required by `23787415`, which has no bypass.
|===

So the accurate statement is narrower than "the bypass is gone" and different
from "three gates are open":

* All **21 distinct required contexts** are unbypassable, because `23787415`
  enforces them all and carries no bypass actor. Lock-Floor and Secret-Scan-Floor
  duplicate two and one of them respectively, so their bypasses discard nothing
  that is not still required next door.
* **`required_linear_history` is genuinely bypassable.** It is the only rule in
  the repository that appears in exactly one ruleset, and that ruleset still
  grants `RepositoryRole:5` bypass mode `always`. Append-only merging is
  therefore still advice for an admin.
* Those two duplicate rulesets should still be cleaned up, not because they
  currently weaken anything but because a redundant bypass is a bypass waiting
  to become load-bearing the day someone removes the check from the main gate.

This is the same failure mode the audit describes, one layer down: the headline
gate was fixed where the symptom was loudest, and three quieter rulesets were
not examined. It is recorded rather than fixed here because it is a
branch-protection write, and because a second unverified ruleset edit on the same
day is how protection gets dropped by accident.

==== The two data-dependent rules cannot be satisfied by writing code

`code_coverage` and `code_quality` are the fourth and fifth instances of the
same defect, and unlike the first three they cannot be repaired in this
repository by any change to this repository's files.

What they require, per GitHub's documentation: GitHub **Code Quality enabled**
for the repository, and then either a Cobertura XML upload through
`actions/upload-code-coverage@v1` (for coverage) or the `CodeQL - Code Quality`
check running on pull requests (for quality). Neither prerequisite is a file in
this tree. Code Quality is a repository setting, and the upload permission is
`code-quality: write`, which no workflow here currently requests.

Measured state of the tree those rules are judging:

[cols="1,1",options="header"]
|===
| Fact | Value

| AsciiDoc files | 756
| Shell scripts | 245
| Shell test scripts | 90
| Rust files | 8, across five separate crates, none with a test file
| Coverage instrumentation available in CI | none (no `kcov`, no `bashcov`)
| `code_coverage` rule | `minimum_coverage: 80`
|===

An 80% line-coverage floor on a repository that is 90% prose and shell, with no
coverage instrumentation for either, is not a threshold that a code change can
reach. Standing up shell coverage is a project, not a tidy, and even then the
number would describe the `scripts/` directory rather than the artifact this
repository exists to produce.

So the honest options are these two, and they are both settings:

. **Remove the two rules** from `23787415`. The repository keeps 21 required
  status contexts, all producible, and the other five rule types.
. **Keep them, but make them true.** Enable Code Quality, add the Cobertura
  upload with `code-quality: write`, and lower `minimum_coverage` to a figure
  the tree actually meets — a floor nobody can reach is not a quality bar, it is
  a permanent block. Note that the coverage rule evaluates only data already
  uploaded and *does not wait* for uploads, so the job that uploads coverage
  must itself be a required status context or the rule can pass on no data.

What is not an option is leaving them as they are: `required_status_checks`
fails every pull request that is otherwise perfect, and that is the precise
failure this entire audit documents. The gate now reports them as
`UNSATISFIED-RULE` so they cannot hide again, but a gate that reports the reason
a pull request cannot merge is a diagnosis, not a remedy.
