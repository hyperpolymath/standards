== Why this exists

On 2026-09-22 a single AI-assisted estate audit filed 91 issues in one day on
this repository, on top of a backlog that already carried ~100 open issues,
most of them unlabelled and mixed across scopes. The audit findings were
genuinely good; the *filing model* was not. The failure mode was:

. one GitHub issue per finding, with no deduplication against the open backlog;
. estate-wide findings (repos, org rulesets, and tooling that do not live in
  this repository) filed *here*, inflating this repo's actionable backlog;
. several waves with no umbrella, so nothing could track or close a wave as a
  unit; and
. the source documents for the findings (two duplicated checkpoint notes that
  disagreed with each other) drifted from the filed text.

Nothing in this repository previously said where a finding belongs, when it
must be merged into an existing issue, or what a batch of findings owes the
backlog. This specification closes that gap. It is normative for this
repository and, as a template, intended for the estate.

== Authority

Normative, derived from link:../0-canon/constitution/AUTHORITY-AND-PRECEDENCE.adoc[Authority
and Precedence] and implementing the communication rules in
link:../0-canon/GOVERNANCE.adoc[GOVERNANCE]. Where a rule below conflicts with
the constitution, the constitution wins and the conflict is recorded per
link:../0-canon/constitution/CHANGE-PROCEDURE.adoc[Change Procedure].

== Definitions

*Issue*::
A GitHub issue on this repository.

*Repo-local*::
The actionable fix lives in a file in *this* repository (a spec, a script, a
reusable workflow, a template seed, a config, a tool).

*Estate-wide*::
The actionable fix lives in other repositories, in organisation rulesets, or in
external tooling. This repository may be the *source* of the fix (it hosts the
template, spec, or reusable workflow that propagates), but the work itself is
done across the estate.

*Wave*::
A batch of findings produced by one audit, campaign, or agent session,
typically filed within a single day.

== The rules

=== Rule 1 — One issue, one actionable defect, correct scope

MUST: a new issue is opened only when (a) it names a defect, decision, or
campaign in *this* repository, and (b) the actionable fix touches a file in
this repository (repo-local) or the source of a fix that propagates from this
repository.

Estate-wide findings MUST be recorded in the estate register — the current
home of the owner-decision register is the open issue labelled
`meta:umbrella` + `decision` (e.g. the "Owner decision sheet D1–D72" issue) —
not as new issues here. If a finding is estate-wide *and* this repository is
the fix source, it is filed here with label `scope:repo` and a *Propagation*
section naming the estates it affects.

=== Rule 2 — Deduplicate before filing

MUST: before filing, search open issues for the same defect (title keywords,
component name, or the `scope:` label). If the defect already has an issue,
the new evidence is added as a *comment* on that issue, not as a new issue. A
finding that is a *different defect in the same component* gets its own issue
and cross-references the sibling.

The 2026-09-22 wave filed, for one component (the actions.lock machinery), at
least six separate issues covering overlapping ground. Rule 2's test: would a
reader of the older issue consider the new finding already covered? If yes,
comment; if no, file and cross-reference.

=== Rule 3 — Waves owe an umbrella

MUST: any wave of more than five findings opens exactly one `meta:campaign`
umbrella issue *first*, stating the wave's source (the audit/checkpoint
documents, by name and hash where possible), its scope, and its acceptance
criteria. Every finding in the wave MUST reference the umbrella.

A wave may not be "closed" until its umbrella's acceptance criteria are met or
its remaining issues are each closed, parked (`status:blocked`), or converted
to the estate register with a comment saying so.

=== Rule 4 — Templates are mandatory

MUST: issues are filed through the templates in `.github/ISSUE_TEMPLATE/`:

* `bug` — a defect. Requires evidence: the command, its output, and the
  expected result. No evidence section, no merge.
* `decision` — an owner ruling is needed. Requires the options, the
  recommendation, and what blocks in the estate on each option. Decisions MUST
  also be added to the open owner-decision register (Rule 1).
* `campaign` — a multi-repo or multi-step effort. Requires the umbrella
  linkage (Rule 3) and a step list.
* `other` — deliberately absent; the blank form is disabled. Anything that
  fits no template does not fit this repository.

=== Rule 5 — Labels are part of the issue

MUST: every open issue carries a `scope:repo` or `scope:estate` label.
`label-triage.yml` applies what the classifier is confident about on new
issues; the filer completes the rest at filing time. An issue without a scope
label is untriaged by definition.

Decision items carry `decision` + `status:needs-ruling` (or
`status:needs-owner`). Time-bounded items carry an explicit date in the body
*and* a `priority:` label matching the date pressure.

=== Rule 6 — Automation may file only under contract

MUST: the only workflows authorised to open issues on this repository are the
designated detectors, and each MUST maintain *exactly one* tracking issue
(re-opened/edited in place, never stacked):

|===
|Detector | Tracking-issue key

|lockfile-drift-detect.yml
|label `lockfile-drift`

|settings-drift-detect.yml
|title match `Settings drift`
|===

Any new automated filer requires a change to this specification (a canon
change), not just a workflow. Detectors report; they do not triage.

=== Rule 7 — No silent closes, no orphaned evidence

MUST: closing an issue as a duplicate names the canonical issue in the closing
comment. Closing an issue as superseded names the superseding issue or ruling.
Evidence that is about to be orphaned by a close (e.g. a mis-triage pattern
worth preserving) is copied into the surviving issue's comment first.

=== Rule 8 — Specs reconcile on contact

MUST: when a finding reveals that a committed spec contradicts another spec or
a committed ruling, the finding MUST be stated as a *contradiction* (per the
constitution's precedence test) and resolved by an authorised change that
identifies what it supersedes — never by amending one side silently so both
sides "hold" in parallel.

== Triage and maintenance (guidance)

* The backlog is reviewed at the start of each campaign week: unlabelled
  issues get a scope label or are closed with a reason.
* `status:needs-ruling` issues older than 30 days are re-presented to the
  owner as a batch (one answer resolves a batch, not 30 tickets).
* Wave umbrellas are the unit of progress reporting, not individual findings.

== Enforcement

Templates and the label classifier implement Rules 4 and 5 mechanically.
Rule 3 and Rule 2 are process rules: the enforcement is the review above, and
any recurrence of a 91-issues-in-a-day shape without an umbrella is itself a
reportable finding against this specification.

A future detector (out of scope for v1.0.0) MAY flag a day on which more than
ten issues opened without a `meta:campaign` umbrella reference.
