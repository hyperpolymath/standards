= ADR-009: Declared egress for secret-bearing jobs, in place of an estate-wide harden-runner
:toc: preamble

[cols="1,4"]
|===
| Status | *Proposed*, step 1 of `0-canon/constitution/CHANGE-PROCEDURE.adoc`. The owner chose the direction on 2026-10-27 through the selector; steps 3 to 6 remain owed.
| Date | 2026-10-27
| Supersedes | nothing
| Authority sought | normative for estate CI: how Hypatia `research_extensions/RE001` is satisfied, and the `(egress …)` clause profile of the repo deed
|===

== The request

Hypatia rule `research_extensions/RE001` reports a `:warn` finding for every
workflow job that references `secrets.*` without installing
`step-security/harden-runner` ("review outbound-egress monitoring"). No estate
repository uses harden-runner. In `hyperpolymath/echo-types`, RE001 remained on
`push-email-notify.yml`, which genuinely needs SMTP secrets, and the owner
deferred that finding to one estate-wide decision rather than add harden-runner to
one repo (hyperpolymath/echo-types#354).

== Context, as measured on 2026-10-27

* *harden-runner is already allowlisted.* `step-security/harden-runner@*` is in
  `config/settings/actions-allowlist.json`, and `verified_allowed` is `true`.
  Adopting it would not have repeated the 2026-10-26 zero-job startup failure. No
  allowlist change follows from this decision either way.
* *RE001 counted the job token.* Its pattern matched `secrets.GITHUB_TOKEN`, the
  same token as `github.token`, which RE001 never counted. In the template,
  `labels.yml` and `label-triage.yml` already use `github.token`.
* *Three template workflows read anything else.* `push-email-notify.yml` (the
  four SMTP secrets), `sonarqube.yml` (`SONAR_TOKEN`) and
  `build-notification.yml`, whose `secrets.BOJ_SERVER_URL` is a URL with a
  `vars.` fallback.
* *Audit mode trades a warning for a high.* RE002 reports harden-runner in
  `egress-policy: audit` on a push-triggered workflow as `:high`. Both
  `push-email-notify.yml` and `build-notification.yml` run on push, so adopting
  in audit mode, as first proposed, would have raised the severity.
* *Privacy.* harden-runner's community tier sends each job's egress telemetry to
  StepSecurity's hosted service. That is a new third-party data flow about every
  run. In block mode, the SMTP job would also have to name a secret host in its
  allowed-endpoints list.
* *Lock cost.* Each job that installs it gains an `actions.lock` entry. The
  template's `labels.yml` deliberately has no `uses:` step for exactly that
  reason.

== Decision proposed

. *Every secret-bearing job declares its egress in the repo deed.* The
  `(egress …)` clause of `<repo>_chora.deed`, with grammar
  `1-formats/deed/spec/abnf/clauses/egress.abnf` (a profile of `deed.abnf`
  v1.2.0, which does not change) and prose
  `1-formats/deed/spec/EGRESS-CLAUSE-SPEC.adoc`. The deed attests a fact about
  the repository, which is its job in the owner's model: contractiles are
  policy, descriptiles are reality, the deed attests both.
. *RE001 accepts the declaration.* A job is satisfied by harden-runner *or* by a
  deed entry whose `:secrets` equal the secrets the job references. Drift in
  either direction is a finding.
. *RE001 stops counting `secrets.GITHUB_TOKEN`.*
. *harden-runner is not adopted estate-wide, and not banned.* It stays
  allowlisted, and it becomes one value of `:enforcement`
  (`harden-runner-audit`, `harden-runner-block`). A repo that wants run-time
  containment adopts it per job, and the attestation records it.
. *The template carries the declarations* for its secret-bearing workflows
  (`push-email-notify`, `sonarqube`, `build-notification`), so every repo minted
  from it inherits them with the workflows. A workflow re-sync does not touch an
  existing repo's deed, so existing repos gain the entries by the sweep in
  <<owed>>. RE001's fix text gives each one the exact `(job …)` entry.

== Alternatives considered

[cols="2,3,3",options="header"]
|===
|Option |For |Against

|Adopt harden-runner in audit mode (as first proposed)
|Run-time telemetry, no allowlist change needed.
|RE002 rates audit mode on a push trigger `:high`, so the finding gets worse. Third-party telemetry about every run. One lock entry per job.

|Adopt harden-runner in block mode
|Strongest run-time containment.
|The same telemetry flow. An allowed-endpoints list per job with no reviewed source, and the SMTP host is itself a secret.

|Don't adopt; blanket exception
|No moving parts.
|Blinds RE001 to every new secret-bearing job. Records no boundary.

|Reduce secret use, then classify the rest as exceptions
|Small change; no new artefact.
|An exception says "we chose not to look". It records no endpoints, so nothing can enforce or check them later.

|*Declared egress in the deed (chosen)*
|The boundary becomes a reviewed, versioned, grammar-checked fact, whether or not anything enforces it yet. Fits the deed/K9 model. No third-party data flow. Any enforcer can be added later, per job.
|New artefact and consumer code. RE001 checks the declared *secrets*, not the declared *endpoints* (see <<owed>>).
|===

The chosen option is the most elegant and correct long-term one (arrival-pack
rule 15), and it is the one the owner selected.

== Compatibility

* `deed.abnf` is unchanged, and so is every existing deed. A deed without the
  clause stays valid.
* RE001 findings disappear for jobs that use only `GITHUB_TOKEN`, and for
  declared jobs. Drift findings are new, with the same rule id and severity.
* Repositories pin standards workflows by SHA. The `deed-conformance.yml` step
  that checks the clause reaches a caller only when it bumps that pin.

== Evidence status

* The ABNF profile was compiled together with `deed.abnf` by an independent
  ABNF engine (apg-js 4.4.0). On the 31 fixtures in
  `1-formats/deed/tools/fixtures/egress/`, it accepted every valid fixture and
  rejected every syntactic violation. It accepted the semantic ones (duplicates,
  port range, a `secret:` endpoint not in `:secrets`, `GITHUB_TOKEN`, missing or
  repeated fields), which the profile marks SEMANTIC and `deed_lint.js --egress`
  rejects. The first run of that check found a real defect: `1*path-char` let a
  possessive repetition swallow the `.yml` suffix. The rule was rewritten so that
  both kinds of parser accept the same strings.
* `bun test 1-formats/deed/tools/`: 104 tests pass, 37 of them for the profile.
  Every invalid egress fixture is asserted to be a grammatical deed, so each one
  tests the profile and not the grammar.
* The Hypatia change carries its own tests (hyperpolymath/hypatia, RE001).

== Tensions introduced

* *One declaration site.* DEED-GRAMMAR-SPEC § _One declaration site_ puts
  vocabulary in `estate_chora.deed` and nowhere else. The `:enforcement` symbols
  are vocabulary, and no `estate_chora.deed` exists yet. Until one does, the
  clause profile ABNF is the only place they are declared. When it lands, it
  declares them and the profile references it.
* *A fact the rule cannot fully check.* The deed attests `:endpoints`, but only
  `:secrets` is compared with the workflow (<<owed>>). An attestation is an
  input, never a conclusion (DEED-GRAMMAR-SPEC, _A self-declaration is an
  input_), and the endpoint half stays an input until it is measured.

[[owed]]
== What remains owed

* *Endpoint verification.* RE001 checks `:secrets` against the workflow, not
  `:endpoints`. Checking endpoints needs a static model of what each action
  reaches, or run-time observation. A one-off harden-runner audit run on a
  branch would measure them without adopting it.
* *The Trustfile policy item.* The template's `trust.k9.ncl` declaration should
  carry the invariant "every secret-bearing job has an egress attestation", with
  RE001 as its probe.
* *Agent instruction.* `coordination.k9` should tell agents that adding
  `secrets.*` to a job means adding or amending its `(egress (job …))` entry.
* *The sweep.* Existing repos whose workflows came from the template need the
  template's `(egress …)` entries in their own deed, through
  `scripts/deed-clause.sh append`, by the same farm sweep that places the
  workflows. Until then RE001 still fires there, now with the exact fix.
* *Repos without a deed.* A repository with no `<repo>_chora.deed` cannot
  declare, so its secret-bearing jobs keep the RE001 finding until it gets a deed
  (hyperpolymath/choreographic-types is one).
* *The ABNF engine check in CI.* The apg-js cross-check was run by hand. Wiring
  it needs a pinned npm dependency in this repository.
* Steps 3 to 6 of the change procedure.
