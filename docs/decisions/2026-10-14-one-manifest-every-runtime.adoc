== Decision

*One manifest, every runtime.*

- `package.json` is the only manifest. Bun, Deno 2 and pnpm all read it
natively: dependencies through their installers, scripts through `bun run`,
`deno task` and `pnpm run`. Nothing is translated, so no second manifest can
drift.
- Each runtime that keeps a lock writes its own: `bun.lock` (tier 1),
`deno.lock` and `pnpm-lock.yaml`.
- npm, the last resort, keeps none (`package-lock.json` stays refused,
standards#67).

*The tool* is `tools/js-runtimes` (Rust). It uses the `ijson-jcs` crate
in-process at a pinned rev.

[cols="1,3",options="header"]
|===
| Command | What it does
| `regen` | The only writer. Makes `package.json` JCS, then regenerates `bun.lock`, `deno.lock` and `pnpm-lock.yaml`, each with its own tool, then re-canonicalises.
| `check bun\|deno\|pnpm` | The gate. Checks JCS, that the lock is present, a frozen install (a stale lock fails), and the `test` script under that runtime's runner.
| `pick` / `run SCRIPT` | The most-preferred runtime on `PATH`, and a `package.json` script run with it. Scripts and tooling follow the order wherever the environment allows.
| `provision` | Every environment definition the repository carries (`mise.toml`, each `Containerfile`, each Guix manifest) provisions Bun. mise and containers can always provide Bun, so settling for less there is a finding. For Guix, the best runtime it provisions is accepted and reported. A `package.json` that no environment definition provisions a runtime for fails.
|===

*The gate* runs in `governance-reusable.yml`: a provision job, and one check
job each for Bun, Deno and pnpm. The same jobs are offered standalone in
`js-runtimes-reusable.yml`. A repository without a `package.json` passes with
a notice naming the denominator (0).

*Deno* is tier 2 and is not gated (§1.3 of LANGUAGE-POLICY). The refusal job,
the pre-commit refusal and the `deno-allow.txt` ledger are retired.

== Consequences

* *JSON-POLICY §6.* It left `package.json` open as a bot-written file:
`bun add` rewrites it in its own layout, undoing JCS. `regen` after
`bun add` / `pnpm add` puts it back, and the gate catches a forgotten run.
* *Once callers bump their governance pin*, every repository with a
`package.json` must carry all three locks and a JCS `package.json`.
Repositories that don't will go red until `js-runtimes regen` is run and
committed, and until their environment definitions pin Bun. The owner chose
this knowingly ("Join governance now").
* *Test scripts must be runtime-neutral.* Each check job installs only its own
runtime, so a `"test": "bun test"` fails the Deno and pnpm legs where Bun is
absent. Where Bun is present, it tests Bun, whatever the leg.
* *Deno does not record `file:` dependencies in `deno.lock`.* A stale `file:`
dependency is caught by the Bun and pnpm legs only (measured 2026-10-14,
Deno 2.9.6). Registry dependencies are caught on all three legs.
* *Pins.*
** Bun 1.4.2 (`oven-sh/setup-bun` v2.2.0) and Deno 2.9.6 (`denoland/setup-deno`
v2.0.5), both SHA-pinned setup actions already in estate locks.
** pnpm 10.28.0, via Corepack pinned by its tarball's sha512. A wrong hash is
refused.
** ijson-jcs: the crate at `3a9a4ee`, and the CLI at `0fdeea71` for the
self-test.
** The pins appear in `js-runtimes-reusable.yml`, `governance-reusable.yml` and
`self-test.yml`, and are bumped together.
* *An earlier draft* installed the runtimes with `npm install -g`. Scorecard
then raised four medium alerts, one per install line, and SonarCloud's
new-code security rating fell to C. Its finding could not be read from the
agent sandbox. The pinned setup replaced it.
