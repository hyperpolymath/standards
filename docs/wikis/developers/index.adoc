==== Green everywhere, still BLOCKED

If every check is green, the review is clear, GitHub says `mergeable=MERGEABLE`,
and `mergeStateStatus` still reads `BLOCKED`, inspect the audit verdict before
choosing a repair. Green checks alone do not establish that a required status
context is missing. Unsatisfied data-dependent rules such as `rule:code_coverage`
or `rule:code_quality` appear as `UNSATISFIED-RULE`; inspect their required data
and repository settings before considering a status-context repair.

[source,bash]
----
# which required contexts can actually be published on a pull request?
bash scripts/check-required-contexts.sh . --json /tmp/rc.json
jq -r '.results[] | select(.verdict == "PR-UNPRODUCIBLE" or .verdict == "UNSATISFIABLE" or .verdict == "UNSATISFIED-RULE") | "\(.verdict)\t\(.context)"' /tmp/rc.json
----

The usual cause is a context name that points at a *call site* rather than a
check. A job that calls a reusable workflow is reported as
`<caller job name> / <callee job name>`, so two workflows running the same
reusable publish two different names — and the ruleset can require the one that
only runs after merge. `PR-UNPRODUCIBLE` in the output is exactly that, and the
verdict comes with the workflow and event list that published it.

When the verdict identifies a context-name issue,
`scripts/fix-required-context-name.sh` reports the
one-line ruleset diff and `--apply` writes it (needs repository admin). Do not
add the missing check to `.machine_readable/required-contexts-allow.txt` unless
it genuinely cannot be produced — that file is a shrink-only list of accepted
debts. It carries no unproducible context; its one entry is a data-dependent
`code_quality` rule awaiting a repository-settings decision no file can make.

==== Decoding a red gate fast

* Read the *step* that failed, not the job title; a job named for a check that
  ends in `|| true` or `continue-on-error` is not a gate at all.
* `gh pr checks <n>` for the rollup, `gh api …/check-runs/<id>/annotations` for
  the actual message. `gh run view --log-failed` often returns nothing useful.
* A check that exists in CI but not in the ruleset cannot block anything. If a
  lane catches a real regression and does not gate, say so — `Repo self-tests`
  caught two in one session and now gates.
